Rewind Together
Version: 1.7.1
Built:   2026-10-15
Game:    Retro Rewind (Steam AppID 3552140)
Engine:  Unreal Engine 5.4
Needs:   UE4SS 3.x

Everyone playing together must be on the SAME version of this mod
AND the same version of the game. If one of you auto-updated Retro
Rewind and the other did not, you will not be able to connect --
Unreal refuses mismatched builds.

Check with:  rt.status   in the game's console (press ~ twice,
type it, press Enter), or the launcher's Play tab.


CHANGES IN 1.7.1  -  the launcher updates itself, checks
                     mods before you join, and shows on
                     Discord.
------------------------------------------------------
  * NEW: one-click updates. When a new version is out, the
    launcher shows a green banner. Press Update: it downloads
    the release from GitHub, checks its SHA-256, replaces
    itself and the mod, and restarts with your saves and
    settings as they were. Not during a co-op session.
    A 1.7.0 launcher can't do this yet, so get 1.7.1 by hand
    once; from then on, Update does it.

  * NEW: mod check before joining. While its store is open,
    the host's launcher publishes its Rewind Together version
    and its other mods through Steam. Before a guest joins,
    their launcher says what differs: another version (red),
    other content mods such as .pak and Blueprint mods
    (yellow), other script mods (a note). "Join anyway" still
    works. Nothing is downloaded.

  * NEW: Discord status. With the Discord app open, your
    profile says "Playing Rewind Together": hosting a video
    store, visiting a friend's store, running the store, or
    in the main menu, with the player count and a link to
    the project. Nobody's name, address or Steam ID is shown.
    Switch it off under Diagnostics.

  * The mod itself is the same as in 1.7.0 apart from its
    version number. Host and guests still need the same
    version.


CHANGES IN 1.7.0  -  tested on two copies of the game at
                     once, and guests can finally work the
                     store.
------------------------------------------------------
  HOW IT WAS TESTED
    Every change below was checked by running a host and a
    guest on ONE PC (the second copy started directly, the
    guest joining 127.0.0.1), driven through a developer-only
    command bridge (devbridge.lua, inert unless its switch file
    exists). Nothing here is from theory alone; each "measured"
    has a log line or a screenshot behind it.

  * FIXED: the host died the moment a guest joined.
    rpcchan.lua passed a Lua string where ClientMessage takes an
    FName. UE4SS does not convert it - it dereferences it, and
    the process dies inside UE4SS (access violation at 0x70).
    Reproduced on demand on a spare copy; FName("...") is fine.
    The test harness now refuses a string for that parameter.

  * FIXED: random crashes 40-150 s into a session, inside Lua's
    garbage collector on garbage pointers. LoopAsync runs Lua on
    UE4SS's own thread while the game thread runs this mod's
    Lua - one Lua state, two threads. The tick loop now uses
    LoopInGameThreadWithDelay (present in this UE4SS build);
    keys are POLLED on the game thread (input.lua) instead of
    RegisterKeyBind, whose callbacks also run off-thread; and
    the left-mouse binding every click went through is gone
    unless the experimental menu button is on.

  * FIXED: guests crashed 1-3 minutes in on an engine worker
    ("Foreground Worker", reading 0xffffffffffffffff), seven
    times, always with NPC looks on. npcsync.lua cached the
    meshes, textures and materials it had loaded in a Lua
    table - and a Lua reference does not keep an Unreal object
    alive. Once the NPCs using an asset despawned, garbage
    collection freed it and the cache handed out the dangling
    pointer. Found by disassembling the crash site and matching
    the offset (+0x560) to the header dump: SkinnedAsset /
    StaticMesh. Assets are looked up fresh every time now.
    Soak: 8 minutes clean, was 109-161 s every run.
    Hardening found on the way, kept: the RPC hooks only queue
    and the mod's tick applies (Chan.pump); body swaps use
    SetSkinnedAssetAndUpdate(mesh, true); material instances
    are never created under a fixed name.

  * FIXED: the mod itself cost frame rate - on every PC, in
    single player too. UE4SS's FindAllOf / FindFirstOf walk
    every object in the engine: 15-17 ms a call, whatever they
    look for. Counted live for 10 s, the mod was spending 60%
    of the host's game thread (53% of the guest's) in them.
    ue.lua now asks the engine directly (GameplayStatics,
    the GameInstance, soft-reference lookups) and keeps the
    walk only as a rare fallback. Measured after: 2.4% on
    both, mostly a backed-off search for listed classes this
    save does not have. On the way, two memory leaks in how
    UE4SS calls engine functions were found and worked
    around (it keeps every out-parameter table forever); over
    an 8-minute session the mod's Lua memory now holds at
    2-4 MB (it had been climbing past 80 MB).

CHANGES IN 1.5.9  -  the engine was putting it back,
                     every frame, and three versions
                     argued with it instead of it
------------------------------------------------------
  * THE FLOATING BODY. The actual cause, after three
    versions of treating a symptom.

    The offset was never failing to apply. 1.5.8's own log
    proved that and nobody read it properly:

      18:56:51  mesh offset Z-90 applied via
                K2_SetRelativeLocation(v,false,{},false)
      18:56:51  measured: the mesh origin sits -90 from the
                pawn's origin (wanted -90)
      18:57:00  rt.bodies -> feet offset: Z+0

    Applied, verified, gone. Because a remote player is a
    SIMULATED PROXY, and ACharacter network-smooths those.
    UCharacterMovementComponent::SmoothClientPosition_-
    UpdateVisuals() does this every frame:

      NewRelTranslation = ...(MeshTranslationOffset +
                              GetBaseTranslationOffset())
      Mesh->SetRelativeLocationAndRotation(NewRelTranslation,
                                           NewRelRotation)

    BaseTranslationOffset is cached by ACharacter from
    wherever the mesh sat at construction. Player_Character_C
    has never had a body in it, so its mesh sits at the
    origin, so the cache is (0,0,0) - which is exactly the
    value the offset kept reverting to, on remote pawns only.

    Every fix since 1.5.6 wrote the component. The engine
    owns that component and rewrites it sixty times a second
    from a number none of them touched.

    So write the cache. BaseTranslationOffset and
    BaseRotationOffset are both UPROPERTY() and take a direct
    write; ACharacter::CacheInitialMeshOffset, the engine's
    own front door for this, is plain C++ with no UFUNCTION
    and cannot be called from here. Smoothing then produces
    the offset we want on its own, every frame, and the body
    interpolates like a real character instead of being
    yanked back into place twice a second.

    Fallback if the cache will not take: NetworkSmoothingMode
    = Disabled, which stops the engine writing the transform
    at all. Costs the interpolation - a remote player steps at
    10 Hz instead of gliding - and that is a fair trade
    against a body at head height.

  * A NOTE ON HOW THIS WENT, because it is the most expensive
    thing in this file.

    1.5.6, 1.5.7 and 1.5.8 each shipped a different fix for
    "the body floats". None of them was wrong about what it
    changed. All three were wrong about what owned the value.
    The measurement that settled it - apply, verify, re-read
    nine seconds later - existed in 1.5.8 and pointed straight
    at "something else writes this", and the next change was
    STILL to write it again, harder, on a timer.

    When a value you set goes back on its own, stop improving
    the write. Find the writer.

  * rt.bodies prints BaseTranslationOffset per remote player
    and marks it when it is the thing flattening the offset.

  * The smoke test now runs a smoothing frame. Setting the
    component without the cache passes every other check in
    that section and still floats in game, which is precisely
    how this survived three releases.

    nothing logged. Steam only puts "+connect" on the command line when it
    LAUNCHES the game for a join. If the client is already running it
    updates GetLaunchCommandLine instead - and the mod only read that once
    at startup, so it never saw the request. It is now polled every 2s.

  * Steam relay was silently not active: the listen server came up on
    IpNetDriver, and a steam.<id> URL means nothing to it, so guests were
    bounced. Added bUseSteamNetworking=True, and the mod now says so
    loudly at host time instead of failing silently - including whether
    the Steam driver class is even loadable in this build.

CHANGES IN 1.1.2
----------------
  * SafeMode is now ON by default, confirmed by live testing: pressing
    F7 to host crashed the game, and turning SafeMode on fixed it and
    allowed a successful invite. The fault is in the runtime-created
    render components (floating nametags and the on-screen overlay),
    not in the networking.
    Everything that makes co-op work is unaffected. Chat and status
    print to the UE4SS console instead of on screen.
    Both players should be on this version - no manual config edit
    needed any more.


CHANGES IN 1.1.1
----------------
  * FIXED: crash at the boot menu. The "PLAY CO-OP" main-menu entry
    constructs a UMG widget at runtime and parents it into the live
    menu; on this build that took the game down the moment the menu
    appeared. It is now OFF by default (Config.ShowMainMenuButton).

    If you do enable it, it now refuses to add itself to a container

  * Join/leave handling no longer fires in single player.


CHANGES IN 1.1.0  (fixes from the first live test)
--------------------------------------------------

CRASHES / PERFORMANCE
  * Removed a hook on /Script/Engine.Actor that fired a Lua callback for
    every actor the game ever constructed - thousands, continuously.
    Only pawns are watched now.
  * Stopped touching actors from inside construction callbacks. Calling
    SetReplicates on a half-built actor reaches into the world's network
    list mid-construction; that was the fatal error. New actors are now
    queued and handled a tick later.
  * The mod is completely inert in single player. It does no work at all
    until a net driver exists.
  * The 5-second sweep no longer does 52 full object-array scans at once;
    it walks 4 classes at a time, round-robin, and skips actors it has
    already handled.
  * Hot lookups (player controller, world, net driver, game mode) are
    resolved once per tick instead of several times each.
  * bAlwaysRelevant now defaults OFF. Having it on made the server send
    every prop in the store to every client on every update.

CORRECTNESS
  * Hosting no longer silently did nothing: the mod was asking
    UKismetSystemLibrary for GetNetMode, which does not exist there, so it
    always believed it was in single player. Net mode is now read from the
    world's net driver.
  * Steam ID was being read as a struct and stringified to
    "table: 0x...". It is now extracted properly, with Steam's own
    loginusers.vdf as an exact fallback.
  * Steam IDs are no longer rounded. Formatting a 17-digit ID as a float
    lost the last two digits, so every join would have failed.
  * PostLogin/Logout hooks were silently unavailable (they are plain C++
    virtuals with no reflection data). Now uses the K2_ variants, plus
    polling that always works.
  * Hosting and joining use GameplayStatics.OpenLevel and
    PlayerController.ClientTravel instead of console commands.
  * The main-menu button now anchors on the menu's own buttons instead of
    a guessed widget class name, and rt.menu reports what it found.
  * A failed host attempt now says so loudly instead of appearing to work.

NEW
  * Config.SafeMode - disables everything that creates render components
    (nametags, overlay) while keeping co-op. Try it first if anything
    misbehaves.
  * rt.menu - diagnoses main-menu button injection.
